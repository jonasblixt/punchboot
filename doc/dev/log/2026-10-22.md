  BOOT0 and BOOT1) showed the boot partition flip in `mmc_part_switch` only lasts until pb's next
  user area access, i.e. one boot. A power loss in the middle of a BOOT0 write boots BOOT1 once,
  then the half-written BOOT0. Restoring the user area before reset/jump (tried first, checked on
  jiffy: the restore CMD6 writes 0x08) fixes the `dev reset` case but makes this worse, so it was
  dropped. Jonas wants: an interrupted BOOT0 write boots BOOT1 until the next update.

  A write to the enabled boot partition enables the other one first. `cm` calls the new
  `bio_write_done()` on STREAM_FINALIZE if every write in the stream succeeded, and `mmc_core`
  enables the written partition. No wire change: the host already finalizes after every part
  write (also failed ones, hence the error tracking). `test_mmc_core.c` (fake card + ROM model)
  failed before the fix (boot 2 after the power loss came from BOOT0) and passes now;
  `test_cm.c` covers when `bio_write_done()` is called.
  Caveats: the fallback copy is the old pb, which still re-enables BOOT0, so the protection holds
  once both partitions have the fix (from an older pb: write BOOT1 first). A host that never
  sends STREAM_FINALIZE never makes the written partition bootable (the 1.x host lived in another
  repo, not checked). Not done (Jonas: USB updates are assumed fine): checking that the other
  partition is valid before enabling it. To check on jiffy: `part write` BOOT0 + `dev reset`
  boots the new BOOT0; a USB unplug during a BOOT0 write + power cycle boots BOOT1, also after a
  second power cycle.

## eMMC boot partition and the ROM log (jiffy)

- The i.MX6UL RM/SRM have no register for the eMMC boot partition. The ROM boots from
  BOOT_PARTITION_ENABLE (EXT_CSD[179] bits 5:3) and nothing changes it before pb's eMMC init, so
  `mmc_core` records it then. First as `mmc_get_boot_part()`, then reworked (D-009, below). Checked on jiffy: BOOT0 after a reset, BOOT1 after a power cycle
  with BOOT1 enabled.
- ROM log: the ROM memory map has a log buffer pointer at 0x1E0 (log in OCRAM, 0x00901d14 on
  jiffy). The format isn't documented. A temporary debug print showed 19 words, the same for a
  BOOT0 and a BOOT1 boot, so it doesn't record the boot partition. Event in bits 31:16, value in
  15:0, read/auth/jump take an argument word. Names follow NXP's ROM event IDs for the i.MX6/7 ROMs
  (from memory, they fit: closed config 0xcc, USDHC, HAB 0xf0, jump 0x80001000); 0x000e0000 is
  unknown and printed raw.
- `src/plat/imx6ul/rom_log.c`: `plat_init` copies the log first thing, `punchboot board command
  dump-rom-log` (jiffy, `pb_id` 0xd3399b11) decodes it. Unknown jiffy board commands now return
  NOT_SUPPORTED instead of OK. `test_rom_log.c` decodes jiffy's real log.
- New F-089: the vendored libc `snprintf` doesn't bound `%x` and spins on unsupported specifiers.
- The SRM is NDA: keep its text out of the repo.
- Reworked after review (D-009): `mmc_get_boot_part()` claimed what the ROM did, which is wrong for
  USB boots, other ROMs (imx8 fallbacks) and other media (imxrt QSPI NOR, MCX N A/B offsets).
  `mmc_core` now only reports `mmc_get_boot_part_config()` (`I mmc_setup: BOOT_PARTITION_ENABLE:
  BOOT1`). `plat_get_boot_source()` returns a kind (storage, USB, UART, debugger, unknown) plus
  the bio partition UUID of the slot. imx6ul: STORAGE only when the ROM log shows a USDHC boot
  with no serial boot mode and no device init/read failure, else UNKNOWN; the other plats return
  NOT_SUPPORTED. jiffy's `board status` prints `Boot source: eMMC BOOT0 (<uuid>)`.
- The ROM log format is documented after all, in NXP AN12853 "i.MX ROMs Log Events" (public): an
  event ID in bits 23:0 (31:24 reserved) plus parameter words, Table 7 for the i.MX6 series, the
  pointer at 0x1E0 for the 6UL, 64 words. My names from memory were partly wrong (0x03xxxx is
  internal use, not DIR_BT_DIS). `rom_log.c` now uses Table 7 and masks the reserved bits.
- uuu boot on jiffy: `0x062001` (manufacture boot from SD/eMMC), device init fail (no SD card),
