## `command-mode.md`, a second pass, and whether it leaves room for another image format

Jonas asked for another review pass, and whether the contract is loose enough for other image
formats than bpak. Read against `cm_main.c`, `wire.h`, `session.py`, `boot.md` 4.4 and 5.6,
`compatibility.md` and the parked pbi draft (branch `pbi-image-format`). The findings first;
what was written in is at the end of this entry.

The format question. Nothing in the session, the gate, the exchange rules, the streams,
`PART_VERIFY` without its flag, `BOOT_PART`, `PART_ACTIVATE` or the keys depends on a format.
Three places are bpak's on the wire and stay so: `BOOT_BPAK` (a header of 4096 bytes, then the
parts as that header lists them), `PART_BPAK_READ` (4096 bytes from the partition's end) and
`PART_VERIFY`'s `bpak` flag. What the contract lacks:

- 5.3 and 5.5 word the two bpak commands as any format's ("the image header a partition
  holds", "the image the host sends"), and section 7 fixes each command's meaning. They mean
  bpak.
- How a second format joins isn't said: its RAM boot and header read are new commands,
  appended; the caps tell a host which formats a build accepts; a bpak command answers
  `NOT_FOUND` (or the header's result) for another format's image, and `NOT_SUPPORTED` in a
  build without bpak. `boot.md` 4.4 already leaves "the host's command" to the second format.
- 4.5 doesn't separate `INVALID_COMMAND` from `NOT_SUPPORTED`. In the code `INVALID_COMMAND` is
  only a number outside the enum (a device older than the command); what a build leaves out
  answers `NOT_SUPPORTED`. A format a build can switch off needs that written.
- The token's transfer is 1024 bytes, and an ML-DSA signature is 2420 or more. A keystore
  with only such keys needs a new method; 3.2's "whoever signs its images can sign a token"
  holds for EC keys.

The rest of the pass:

- 5.3 says every command that names a hidden partition answers `NOT_FOUND`, "the boot commands
  too"; `boot.md` 5.6 takes the UUID `BOOT_BPAK` names as given. One of them needs the
  exception.
- 4.1 lists where a transfer's size comes from (the command, a result, fixed). `BOOT_BPAK`'s
  parts are a fourth: the header the host sent. And the two sides agree on a part's bytes, not
  on its transfers: the device reads `CONFIG_BOOT_LOAD_CHUNK_kB` at a time (1 MiB on the 8MP
  EVK), hosts send the caps' largest transfer (4 MiB). Section 6 asks for whole transfers of a
  size both sides know. Read in the code, not run.
- 4.4 doesn't say what follows a part's result that isn't OK in `BOOT_BPAK`. The code reads
  every remaining part after a hash error and answers each, and hosts only check the last.
- 3.3: whether a refusal before the data (an unknown method, a bad size) drops an
  authenticated session and waits the 1 s. The code drops it for a bad size and not for an
  unknown method.
- 5.1 leaves out the caps' `bpak_stream_support`: frozen, zero in every release, never
  implemented.
- Low: `PART_BPAK_READ` on a partition below 4 KiB (the header's block wraps in the code);
  4.5's `NOT_FOUND` for "no image header" is `PART_BPAK_READ`'s, the boot commands answer
  `ERROR` for a bad header.

## `struct board`'s objects (F-265)

Jonas: go on with F-265 after the commits, without questions. What the contract left open is
decided here and listed for him.

- **The objects.** `ptbl`, `boot_policy`, `boot_handover` and `boot_delivery` are members by
  value: a pointer to the module's functions and one to the board's configuration
  (`pb/ptbl.h`, `boot/policy.h`, `boot/handover.h`). A module's macro is a brace initializer,
  not a compound literal, so it is a constant in the board's `const struct board`.
  `PB_CONFIG()` (`utils_def.h`) makes it a compile error when a board hands a macro another
  module's configuration, or NULL, which a `const void *` alone would take: a member that is
  absent is left out, not set to a macro of NULL. `PTBL_GPT()` doesn't compile with a
  pointer where it takes the array's size.
- **The macros.** `PTBL_GPT(device, tables)` takes the number of layouts from the array.
  `PTBL_STATIC(device, table)`, `PTBL_STATIC_MAPPED(device, base, table)`, `BOOT_POLICY_AB()`,
  `BOOT_HANDOVER_IMAGE()`. Two that the contract doesn't have and that go with their
  findings: `BOOT_HANDOVER_ATF()` (F-258, it becomes the delivery) and
  `BOOT_HANDOVER_SIMPLE()` (F-259).
- **`src/board.c`** includes no module's header and has no `CONFIG_BOOT_*` or
  `CONFIG_PARTITION_GPT` left. The order and what a failure does are as before.
- **The modules are as they were.** The policy's functions are the three callbacks the core
  had (get, activate, status): `boot_policy_*()` is F-256. A board that sets `boot_delivery`
  is refused: no delivery exists before F-258. `struct boot_driver` and `boot.c` aren't
  touched.
- `struct boot_driver_linux_config` is `struct boot_handover_image_config`, in a commit of
  its own before this one, so that the boards' lines don't change again with F-258.
  `boot/linux.h` had no include guard; it has one.

Decided where the contract was silent, or where two documents differ:

1. **A board with two tables** (the host: a GPT and its flash's static table). `ptbl` is one
   member. It is the GPT, which command mode installs; the flash's table stays in the
   board's `init()` (`board.md` 2.4, "Absent", has a paragraph for it).
2. **The device a table is on is visible only, with every kind of table.** `bio.md` 2.4 says
   the core takes `WRITABLE` from it; the code did so for a GPT only. The RT's NOR device

   ends a host's writes to the flash outside the table's partitions (264 to 512 KiB, and

   look at `WRITABLE` (F-188). Nothing in the tree addresses the raw device. The host board
