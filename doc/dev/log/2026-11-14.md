## The 8X's logs: the SECO's events, and what else there is (Jonas: "add a log source for SECO events")

What the A35 can read on the 8X, from AN12853, the SCFW API guide (QX B0), the SECO API guide
and the 8QXP RM and SRM:

- **The SECO's events**: yes, `sc_seco_get_event()`. Index 0 takes the SECO's events, the
  next indexes read them, an error ends them. An event is the SECO's response to any request
  that wasn't a plain success since it started: the request in bits 23:16, the indication in
  15:8. The SECO keeps a few (8 on the B0); later ones are lost.
- **The SCU ROM's event log** (AN12853, definition version 3, four buffers of 128 words on the
  QXP B0, 160 on the DXL): no. The ROM runs on the SCU and the log is in the SCU's TCM, which
  the SCFW locks to all but the MUs through the XRDC (RM 2.2.8.1); no SCFW call returns it.
  An OEM SCFW could hand it out through `board_ioctl()`, which would be a board's.
- **The SCFW's own output**: no. It goes to the SCU's UART (`sc_misc_debug_out()` writes a
  character there, nothing reads back), the RM dump too. No log call.
- **A SECO debug dump**: the SECO API has one, the SCFW API doesn't carry it.
- Not logs but state the SCFW gives: the build info of the SCFW and the SECO (the MEK's board
  status prints them), the boot type, device and container set (`sc_misc_get_boot_*()`, the
  material for the 8X's `plat_get_boot_source()`, F-251), the reset reason (already used) and
  the partition that caused it (`sc_pm_get_reset_part()`, not used), the ROM patch checksum.

What changed:

- **The log `seco`** (`src/plat/imx8x/seco_log.c`): the life cycle (`sc_seco_chip_info()`)
  and the events, a line each, read once at the first read. Registered by `plat_cm_init()`,
  not on the boot path (D-023); the two `plat_cm_init()`s became `cm_usb_init()`s under one.
  The requests, indications and statuses are named from the SECO API guide's tables (Jonas:
  name them in the public tree, though the guide is confidential), the life cycles as U-Boot's
  `ahab_status` names them. Unit test `test_imx8x_seco_log`.
- **`vsnprintf()`** in pb's libc: `snprintf()`'s body (TF-A, BSD-3) is `vsnprintf()`, and
  `snprintf()` calls it. Jonas: "fine to add vsnprintf". `test_snprintf` covers it.
- **`punchboot log <tab>`** completes the device's logs from its list; a device that can't be
  asked completes `pb` (Jonas, the same session). The completion test helper skips the empty
  line click prints when nothing matches.
- **The HAB log's writer** is `vsnprintf()` now; its comment said the firmware `%x` doesn't
  check the buffer size, which F-089 (`c6744cc1`) had fixed. Same text, same truncation.

Verified: 94 of 94 on the host, the 8QXP MEK, 8DXL EVK, jiffy, 8MP EVK and RT1060 builds. On
the MEK (Jonas: "yes" to flashing it): the test bench's `pb_signed.imx` written to BOOT0 and
verified, BOOT1 keeps `bc640ba1`; after `dev reset` `log --list` has `seco`, and `log seco`:

```
SECO life cycle: NXP closed (0x0020)
Event 0: 0x0087fa00, command: authenticate container (0x87), indication: bad key hash (0xfa), ...
```

The MEK is open with no SRK fused, so the container's key hash can't match: the SECO notes it
and goes on (status success). `log <tab>` against it offers `pb` and `seco`.

## The 8X's builds and temperature in the log, the boards' status goes (Jonas: "print the scfw and seco ... at boot, then remove the status command")

- `plat_init()` logs the SCFW's build and commit, the SECO's version and commit, the SoC id
  and revision and the temperature (`imx8x_log_info()`), after the MMU is on. On the MEK:

```
[8.345] I imx8x_log_info: SCFW 5665 (654907b6), SECO 196741 (c9de51c0)
[8.352] I imx8x_log_info: SoC id 2, rev 1
[8.367] I imx8x_log_info: Temperature 31.5 C
```

  The boot pays ~40 µs for it (`MMU on` to the CAAM's init: 88 µs, 49 µs before). On the boot
  path against D-023, by Jonas's choice: it is the boot's record of the firmware it ran on.
- The MEK's and the 8DXL EVK's `board_status()` went: `board status` answers the default
  "Board status OK!" (checked on the MEK). `imx8x_plat()` stays, nothing in the tree uses it
  now. `test_plat_imx8x` links the SECO's client.

Verified: 94 of 94, both 8X boards build, the MEK runs it from BOOT0 (BOOT1 keeps `bc640ba1`).

## The 8X's named command `info` (Jonas: "a 'status' command in the platform code", then "call this command info")

- `plat.c` declares `info` with `DEFINE_COMMAND()`: the same information as the boot log
  (`imx8x_read_info()` reads it for both), read again at each call, as text with its NUL. A
  temperature the SCFW can't read is "not read". The first platform command; a board of the
  8X can't have a command of that name now (the list's check, command-mode.md 5.6).
- `test_plat_imx8x`: the SCFW model answers the build and the temperature; the text, a
  temperature below zero, an unread one, and a response cut to its room.
- On the MEK, from BOOT0: `command list` has `info`, and `command info`:

```
SCFW 5665 (654907b6)
SECO 196741 (c9de51c0)
SoC id 2, rev 1
Temperature 31.5 C
```

The first `command info`, 3 s after the MEK enumerated from its reset, timed out (20 s);
`dev show` and `command info` after it answered, and five rounds of `command list` and
`command info` did too. Taken for the MEK's USB right after a reset (F-172: wait ~5 s).

Verified: 94 of 94, both 8X boards build.
