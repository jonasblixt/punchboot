# 2026-10-30

## pb instantiates the CAAM's RNG (F-154)

- `imx_caam_rng_init(ctrl_base)` in `src/drivers/crypto/caam/imx_caam.c`, called by jiffy,
  imx8mevk and imx8mpevk after `imx_caam_init()`; failures are logged, the boot goes on.
  The i.MX8X boards don't call it (SECO owns the RNG, pb only has JR2).
- Why prediction resistance: Linux 6.18 leaves a state handle alone only if RDSTA has both IF and
  PR for it; otherwise it tears it down through DECO 0, which non-secure Linux on the 8MP can't
  acquire. So pb instantiates both handles with PR, generates the secure keys, and uninstantiates
  a handle it finds without PR (from the ROM, say) first.
- The TRNG setup and sequence follow NXP's BSD-2-Clause OP-TEE driver; nothing from Linux.
  RTSDCTL reads zero outside program mode (6UL SRM 6.10.44), so the "never shorter than the
  programmed entropy delay" check reads it in program mode (the first version didn't).
- `tests/unit/test_imx_caam.c`: a model of the controller page, JR0 and the state handles runs
  the RNG operations of each job; 11 tests (fresh, already done, no PR, entropy retries and
  giving up, a kept delay, a job timeout, one handle, no RNG4, era 10).
- On the boards: `rng-caam` on both, RDSTA 0x40000033, `crng init done` at 0.150 s (8MP) and
  0.271 s (jiffy), no instantiation by Linux. 27.3 ms (8MP) / 27.5 ms (jiffy) in pb on every
  boot: a watchdog reset and the EVK's remote reset both clear the CAAM.
- Left: imx8mevk untried. F-155 (the EVK's FEC) left for later (Jonas).
