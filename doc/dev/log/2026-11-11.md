## Where else contracts pay off

Jonas asked where else a contract makes sense, after the platform's (D-030). The criteria: several
implementations of one interface (the review's cohesion findings are that shape), consumers outside
the tree or the release, security resting on the boundary. Where none holds, header comments do.

Proposed, in order: the board (the platform's sibling, out-of-tree boards, 3.0.0's porting API);
block devices (`bio`: F-182, partial blocks without an owner, the block size three ways, F-188,
F-194, F-198; testable on the host against the card models); the crypto backend (F-181, no abort,
two backends); the USB device controllers (three, with F-184, F-201, F-203, F-204, F-205, F-172);
one rule for DMA and caches that those point to (F-184, F-205, F-207, F-220). Into the whole
bootloader's contract: command mode's semantics per command (F-186..F-190) and the OS side of A/B.
Not a contract but an inventory for `compatibility.md`: what outlives a release (the A/B state's
on-disk format, which `compatibility.md` doesn't list; the device identity, the slots, the fuse
layouts, the partition UUIDs). Not proposed: single-implementation drivers (DDR, usdhc, OCOTP,
FlexSPI, the console). Contracts that can run on the host come with a conformance suite run against
every implementation, the fakes too: F-182 hid behind fakes stricter than the driver.

Open from it (asked, not answered): one `drivers.md` or a file per class; whether factory lines
script the CLI (then its exit codes and output fall under D-008, F-225).

## The boot contract, round 2

Jonas's answers (`/tmp/comments2.txt`): the generic handover (Firmware Handoff) carries either a DT
or a pb structure, never both, and pb doesn't make a DT: the image has one when it's needed. One
boot source policy at a time, chosen in Kconfig; the order of the staggered chain is the board's.
The handover's content is assembled centrally, `dtb.c` stays. A trial slot that fails to load
falls back for this boot and is tried again until its attempts run out. Speculative mode, the
idea: when the normal policy has no viable candidate and the option is on, alternate A and B best
effort, so that the system can take an OTA update, and say so in the handover. `pbstate`: the
shared core, `rz[]` extensions and FWU as a model, yes (roadmap); the name stays (my call, noted
there). XIP and CUSTOM: my proposal for now. The board picks the handover. BL32 is OP-TEE today, the
door stays open. The DXL moves to the TF-A handover. Firmware Handoff's AArch32 convention on
Cortex-M. `CONFIG_BOOT_DTB_HEADROOM`'s default is fine. Security > boot time > little code
(`principles.md`).

Xen, from xenbits (`misc/arm/booting.txt`, `misc/arm/device-tree/booting.txt`): dom0's kernel and
ramdisk are `/chosen` module nodes (`multiboot,module` plus `multiboot,kernel` or
`multiboot,ramdisk`, `reg`, optional `bootargs`); `xen,xen-bootargs`, `xen,dom0-bootargs`, and
`/chosen/bootargs` is dom0's unless those say otherwise. Xen follows Linux's zImage/Image protocol
and must be entered in Non-Secure EL2 (HYP) with the MMU and D-cache off, `SCR_EL3.HCE` set: from
pb at EL3 only through TF-A. The docs don't say who writes the module nodes.

## The boot contract, round 3

Jonas: the staggered chain is stateless for now (it protects against an image that doesn't load
or verify, not against one that verifies and crashes); A/B's fallback when nothing is viable is
command mode or speculative, in Kconfig, recovery later; speculative as proposed (only with no
viable candidate, never an image that fails verification, alternates per boot persisted before the
load, no attempts, ends when the OS confirms a slot, the handover says so, no format change) and
it depends on the watchdog. The transfer list: in an image part with a DT, at board level for the
pb structure. The handover model: an entry, four arguments and what it wrote; TF-A delivers BL33's
and BL32's. Xen: a DT prepared when the image is built, no check in pb. The board's DT hook keeps
the whole tree. `pb,boot-partition` and `pb,boot-mode` in `/chosen`.

Firmware Handoff, from its rst sources (FirmwareHandoff/firmware_handoff, `register_conventions.rst`,
`transfer_list.rst`): AArch64 x0 = the FDT or 0, x1[31:0] = 0x4a0fb10b, x1[39:32] = 1 (convention
version), x2 = 0, x3 = the list; AArch32 r0 = 0, r1[23:0] = 0x0fb10b, r1[31:24] = 1, r2 = the FDT or
0, r3 = the list. The FDT must be inside the list (tag 1), the register points into it. List header
0x18 bytes (signature, checksum, version 2, hdr_size, alignment, used_size, total_size, flags),
entries 8-byte aligned (3-byte tag, hdr_size 8, data_size). Tags 0..0x7fffff are allocated in the
spec, 0xfff000..0xffffff are non-standard and discouraged except for experiments and closed
components. No pointers into the list (it may be relocated). Nothing about M-profile. TF-A's tag
0x102 (AArch64 entry point info) is a standard alternative to `bl_params`.
