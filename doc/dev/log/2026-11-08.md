# 2026-11-08

## bpak 1.0.1

bpak 1.0.1 is released (the first on PyPI; 1.0.0's upload failed). punchboot uses it everywhere:
- Dev container: the 1.0.1 CLI is the `bpak` package from PyPI in `/opt/venv`. Upstream's C CLI is
  gone, so the tarball build is gone too. Nothing in the container linked libbpak.
- `bpak generate keystore --decorate` output is unchanged apart from whitespace (no trailing
  spaces, no blank line) and the version comment. Note: `build-<board>/keystore.c` has no make
  dependency and is never regenerated; delete it (and `keystore.d`) to pick up a new CLI.
- Golden images `tests/compat/bpak/v1.0.1/` from `generate.sh`. All boot from RAM and from a
  partition, `dont-hash` xfails like the 0.9.3 one (F-076).
- Test bench: `PB_TESTBENCH_BPAK_BRANCH` is `master` (`work-1.0.0` is merged). Not built.
- Vendored library: `scripts/sync-bpak 1.0.1` copies `lib/bpak.c` and the four headers from the
  tag, formats them with the pre-commit clang-format and generates `include/bpak/version.h`.
  No local edits: `include/bpak/build_config.h`, `src/lib/internal.h` and
  `include/libc/unistd.h` are punchboot's. `PACK()` is no longer used by the bpak headers.
- D-024 records what the firmware rejects now (empty slots between used ones, unaligned meta,
  `pad_bytes` >= 512, size overflows, `signature_sz` > 512, id 0 lookups) and why none of it
  booted or came from a released CLI. Unit tests for each, and for F-011 and F-068 (fixed).
- Checked: `scripts/pbdev test` (32/32), `PB_SANITIZE=ON` fails only on F-152 (open, `mmc_sd.c`),
  firmware builds for jiffy, imx8dxlevk, imx8mevk, imx8mpevk, imxrt1060evk. jiffy's `pb.bin`
  stays 110592 bytes (`bpak.o` +1.1 KiB text, inside the padding).

### On jiffy

The signed `pb_signed.imx` of this branch (bpak 1.0.1) in BOOT1, `part verify` OK, `dev reset`
boots it (console on `/dev/ttyUSB1`). Boot partitions can't be read back (no read flag), so the
fallback was a signed build of `2d338a46` for BOOT1 or `uuu`; not needed.
- `auth token` (P-256 in the CAAM, keystore from the 1.0.1 CLI): OK.
- The test bench's `boot.bpak` (bpak `work-1.0.0`) repacked with the 0.9.3 CLI (the old
  container image) and the 1.0.1 CLI by `post-image.sh`'s commands: all three are byte for byte
  the same (deterministic ECDSA), so one boot covers all of them.
- `boot bpak` from RAM: verified, Linux and kickstart start, kickstart restarts as expected (no
  `pb,active-system`, no system enabled). `boot partition` System A (the same image): login,
  `/` on `/dev/mapper/kickstart-root`, `pb,active-system` A, no errors in `dmesg`; `reboot` is
  back in command mode in 4 s, `log linux` has the `Shutdown` record.
- Headers changed from that image: a part after an empty slot and meta data at an unaligned
  offset fail with `-PB_ERR_BAD_HEADER` before the key lookup (the new validation); one changed
  kernel byte passes the signature and fails the payload hash (`-PB_ERR_BAD_PAYLOAD`).
- Left as found: no system enabled, command mode. BOOT1 has this branch's pb, BOOT0 untouched.

### On the 8MP EVK

A clean `imx8mp_image` build of this branch (the real FW2020.06 training firmware) in BOOT0,
`part verify` OK, `dev reset` boots it. Trap: an earlier build with the placeholder firmware
left `pb.bin` "up to date" when `IMX8M_FW_DIR` was set later; make doesn't track the firmware
directory, so delete `build-imx8mpevk/` (keep the firmware) before a real build. Before the test
the EVK reset-looped in command mode because its download USB wasn't connected
(`Transport init error (-2)`, the 10 s `CM_TRANSPORT_READY_TIMEOUT`).
- The test bench's `boot.bpak` repacked with the 0.9.3 and 1.0.1 CLIs: byte for byte the same
  again.
- `boot partition` System A through TF-A v2.12: login, `/` on `/dev/mapper/kickstart-root`,
  `pb,active-system` A; `reboot` back in command mode in 3 s. `boot bpak` from RAM: TF-A, Linux,
  kickstart, which restarts as on jiffy. `dmesg` has `clk: failed to reparent gic to
  sys_pll2_500m: -16` (Linux's clock tree, not from this change; not recorded before).
- Part after an empty slot, unaligned meta data: `-PB_ERR_BAD_HEADER` before the key lookup;
  a changed kernel byte: signature OK, `-PB_ERR_BAD_PAYLOAD`. pb stays in command mode (F-128
  didn't show: the failure comes after the header is read).
- Left as found: no system enabled, command mode, BOOT0 has this branch's pb, BOOT1 untouched.
