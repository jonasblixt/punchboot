## bpak 1.0.1

bpak 1.0.1 is released (the first on PyPI; 1.0.0's upload failed). punchboot uses it everywhere:
- Dev container: the 1.0.1 CLI is the `bpak` package from PyPI in `/opt/venv`. Upstream's C CLI is
  gone, so the tarball build is gone too. Nothing in the container linked libbpak.
- `bpak generate keystore --decorate` output is unchanged apart from whitespace (no trailing
  spaces, no blank line) and the version comment. Note: `build-<board>/keystore.c` has no make
  dependency and is never regenerated; delete it (and `keystore.d`) to pick up a new CLI.
- Golden images `tests/compat/bpak/v1.0.1/` from `generate.sh`. All boot from RAM and from a
  partition, `dont-hash` xfails like the 0.9.3 one (F-076).
- Test bench: `PB_TESTBENCH_BPAK_BRANCH` is `master` (`work-1.0.0` is merged). Not built.
- Vendored library: `scripts/sync-bpak 1.0.1` copies `lib/bpak.c` and the four headers from the
  tag, formats them with the pre-commit clang-format and generates `include/bpak/version.h`.
  No local edits: `include/bpak/build_config.h`, `src/lib/internal.h` and
  `include/libc/unistd.h` are punchboot's. `PACK()` is no longer used by the bpak headers.
- D-024 records what the firmware rejects now (empty slots between used ones, unaligned meta,
  `pad_bytes` >= 512, size overflows, `signature_sz` > 512, id 0 lookups) and why none of it
  booted or came from a released CLI. Unit tests for each, and for F-011 and F-068 (fixed).
- Checked: `scripts/pbdev test` (32/32), `PB_SANITIZE=ON` fails only on F-152 (open, `mmc_sd.c`),
  firmware builds for jiffy, imx8dxlevk, imx8mevk, imx8mpevk, imxrt1060evk. jiffy's `pb.bin`
  stays 110592 bytes (`bpak.o` +1.1 KiB text, inside the padding).

## MCU test bench (D-025)

Jonas asked for a test bench for MCUs; Buildroot doesn't fit. `testbench/mcu/`: a bare metal test
application (`arm-none-eabi`, built in the dev container, `make -C testbench/mcu`) and a pytest
runner on the host (`testbench/mcu/README.md`). First board: the RT1060 EVK.

pb, on the way (each its own commit):
- F-055 fixed (`6a1a0e23`): `bio_erase()` took the LBA as it was. Command mode worked only because
  hosts send the partition's first block; `ab_state` erasing its block 0 would have erased the
  RT1060's FCB. Now relative with a range check, `cmd_part_erase()` converts what hosts send (the
  2.x transcript), so released hosts erase the same blocks.
- `ab_state` erases the state block first on NOR (`BIO_FLAG_ERASE_BEFORE_WRITE`).
- armv7m: `arch_jump()` sets VTOR and passes r0-r3; the armv7m driver can run an image from RAM
  (the load address of its part), passes the system's name (r0) and the boot partition UUID (r1),
  cleans the D-cache over the image and invalidates the I-cache (the ROM turns both on: CCR
  0x30000 at the image's entry).
- RT1060 EVK: A/B from the NOR (BL, two 4 KiB state copies, System A at 512 KiB and B, 1 MiB
  each); command mode on request (`PB_CM_REQUEST` in SRC_GPR5, RM 21.6.9). The old layout's
  `SBL1` held about 27 KiB of an older application (MQTT strings): dumped over the J-Link to
  `build-imxrt1060evk/nor-backup-2026-11-08/` before the new layout overwrote it. `Config`,
  `Application` and `SBL2` were erased.

The application runs from OCRAM2 at 0x20210000 (the ROM keeps 0x20200000-0x20207fff, RM 9.5.1)
and writes the boot state with the ROM's FlexSPI NOR API (RM 9.13) and pb's FCB. Runs, on the EVK:
- Boot from command mode, A and B: every handover check passes (r0/r1, VTOR, MSP, CONTROL,
  FAULTMASK, no interrupt, SysTick off, nothing pending, WDOG1 running 30.5 s, LPUART1).
- The enabled system boots after a reset, marks itself verified, comes back on request.
- Rollback: B enabled, unverified, 2 attempts: B, B, then A with the B rollback error.
- Watchdog: a hanging B is reset by WDOG1, then A; 36 s.
All 6 in 60 s. Found F-159 (the MEK's pb 2.0.0 serial descriptor) and F-160 (log only).

## RT1060 boot time

Measured on the board: `app-boottime.bpak` stores a clock that runs through the warm reset just
before its `SYSRESETREQ` and reads it at its entry, 10 times (`pytest tests -k boot_time -s`).
Warm reset to the image's entry: 40.13 ms, all 10 within one SRTC tick (30.5 us). pb's steps from
`scripts/boot-time-image -s 4K,8K` (now KiB sizes, an erase first on NOR partitions, the RT1060's
load address): init 0.28 ms, header 0.30, signature 25.9 (SHA-256 + ECDSA P-256 in Mbed TLS),
the 5.2 KiB image 0.9; the rest, 12.7 ms, is the ROM loading pb (75 KiB) from the NOR and pb up
to its timer. 200 KiB verify in 59 ms (the NOR reads 14 MiB/s).

On the way, the RT1060's SNVS:
- The HP real time counter is cleared by the warm reset (it counts again from 0, `RTC_EN` set by
  the image), the LP SRTC keeps running: that is the clock.
- The LP general purpose registers (0x100.., and the 0x90 alias) don't keep a write from the
  core, LPLR is 0, LPSR shows PGD (0x40000008) and writing 1 doesn't clear it. The words are in
  DTCM (its last 16 bytes), which the warm reset keeps.
- The debugger gets bus errors on all SNVS LP registers (its accesses aren't privileged).
- The first `boottime` image had no guard: with the words not kept it reset forever; halting
  it over the J-Link and writing the command mode request got the board back. It now stops
  with a FAIL when the words don't read back.
- `scripts/boot-time-image`'s reset timing (host, to pb's banner) doesn't work on the RT1060:
  the banner comes before the `dev reset` CLI returns.

Next for the boot time: the signature (Mbed TLS settings, `MBEDTLS_ECP_*`), and the ROM's 12.7 ms
(the FCB's read clock and the size of pb).

The MEK (B0 silicon, SCFW 1.18, SECO 5.9.4.1) ran pb 2.0.0 from eMMC; the new host works with it
(F-159 aside, a scratch wrapper picks the device whose serial can't be read).
- pb 3.0.0 (`pb_signed.imx` from the test bench: the container, AHAB signed) to BOOT0 through pb
  2.0.0: it boots (`BOOT_PARTITION_ENABLE: BOOT0`), eMMC in HS200, USB command mode.
- F-159 is in today's cdns3 driver: EP0 at 512 byte packets. 64 made every transfer longer than
  one packet hang, so enumeration stopped at the serial string and the watchdog reset the board
  in a loop (also with EP0 configured again on connect/reset, and with a TRB burst length). Jonas
  set the switches to serial download; pb loads over `uuu SDPS: boot -f`, every reset lands in
  the ROM loader. Back to the committed driver (512) in BOOT0; the attempts are in F-159.
- System A and Root A from the test bench, `boot partition` A: TF-A's memory regions confirm the
  DTS (0x80000000-0xffffffff, 0x880000000-0x8bfffffff), Linux, kickstart, the dm-verity root,
  login on the first boot. The kernel at 0x86000000 overlapped the VPU encoder's reserved memory:
  now 0x80200000, everything below 0x84000000.
- Checks: `/` on `/dev/mapper/kickstart-root`, `pb,active-system` A, `pbstate-pb -i` A verified,
  `imx_sc_wdt` active (60 s, the TF-A SIP calls), `kill -STOP` of pb-watchdog: panic on the
