# 2026-11-08

## bpak 1.0.1

bpak 1.0.1 is released (the first on PyPI; 1.0.0's upload failed). punchboot uses it everywhere:
- Dev container: the 1.0.1 CLI is the `bpak` package from PyPI in `/opt/venv`. Upstream's C CLI is
  gone, so the tarball build is gone too. Nothing in the container linked libbpak.
- `bpak generate keystore --decorate` output is unchanged apart from whitespace (no trailing
  spaces, no blank line) and the version comment. Note: `build-<board>/keystore.c` has no make
  dependency and is never regenerated; delete it (and `keystore.d`) to pick up a new CLI.
- Golden images `tests/compat/bpak/v1.0.1/` from `generate.sh`. All boot from RAM and from a
  partition, `dont-hash` xfails like the 0.9.3 one (F-076).
- Test bench: `PB_TESTBENCH_BPAK_BRANCH` is `master` (`work-1.0.0` is merged). Not built.
- Vendored library: `scripts/sync-bpak 1.0.1` copies `lib/bpak.c` and the four headers from the
  tag, formats them with the pre-commit clang-format and generates `include/bpak/version.h`.
  No local edits: `include/bpak/build_config.h`, `src/lib/internal.h` and
  `include/libc/unistd.h` are punchboot's. `PACK()` is no longer used by the bpak headers.
- D-024 records what the firmware rejects now (empty slots between used ones, unaligned meta,
  `pad_bytes` >= 512, size overflows, `signature_sz` > 512, id 0 lookups) and why none of it
  booted or came from a released CLI. Unit tests for each, and for F-011 and F-068 (fixed).
- Checked: `scripts/pbdev test` (32/32), `PB_SANITIZE=ON` fails only on F-152 (open, `mmc_sd.c`),
  firmware builds for jiffy, imx8dxlevk, imx8mevk, imx8mpevk, imxrt1060evk. jiffy's `pb.bin`
  stays 110592 bytes (`bpak.o` +1.1 KiB text, inside the padding).

Left: boot a signed image on jiffy and the 8MP EVK with the new library; build the test bench
against bpak `master`.
