## The whole project reviewed (F-181..F-232)

Jonas asked for a review of the whole project: bugs, cohesion, documentation and design gaps,
best practices. Eight reviewers in parallel, one per area (security core, command mode, host
tools, storage, arch and platforms, boards, drivers, build/CI/docs), each with `findings.md` to
skip what is recorded. No code changed; their probes are in the job's tmp, not in the tree.

- 52 new rows, F-181..F-232, most of them "Reported": read by a reviewer, not checked again.
  "Reported (probe)" ran against a model or a fake. Checked by me in the code: F-182, F-183,
  F-184, F-211.
- First: F-181 (the CAAM runs one job behind after an abandoned hash: a signature check passes on
  the previous job's status; shown in a model, not on hardware), F-182 (eMMC writes that aren't a
  block multiple lose their tail), F-183 (a changed keystore isn't rebuilt).
- F-184 is a suspect for F-172 (the MEK's write resets): the terminating TRB isn't cleaned.
- F-055 is marked fixed, its WRITABLE part is open (F-188).
- Coverage is 91.0%, not the 99.2% in `testing.md` and `status.md` (F-230).
- Cohesion, in short: partial blocks have no owner (bio rounds up, mmc down, the fakes are byte
  exact); the crypto API has no abort; command mode sends results from three places; the three
  UDCs implement different contracts; block size is hard-coded three ways; the cache API is
  declared per arch; board-as-data holds for the order and the security wiring, console, storage
  and USB bring-up are still code per board.
- Solid: the order of checks on the boot path, the fail-closed RoT/SLC, the wire and bpak guards,
  the 64-bit bio range math, the dwc3 driver, the v8a/v7m handover, a reproducible `pb.bin`.
