# Audit: complexity, duplication and stale assumptions (2026-11-18)

A record of one audit, not a contract. The tree is `work-3.0.0-mega` at `a4992d63`, and every line
number below is from that commit. The audit changed nothing: each item says what the smallest change
would be and how to check it.

The question (Jonas, 2026-11-17): what in the tree is unnecessary complexity, duplicated logic, or
an assumption that no longer holds, with evidence for each; then the smallest change that preserves
behaviour.

## 1. Result

There is little to remove outright. The bigger opportunity is duplicated logic, and the largest
literal duplication (the boards' data) is deliberate.

| Section                           | Items        | Size                                           |
| --------------------------------- | ------------ | ---------------------------------------------- |
| 3 Dead                            | A-01 to A-19 | About 300 lines of files, 60 of statements     |
| 4 Assumptions that no longer hold | A-20 to A-36 | 9 in code, about 130 lines of text             |
| 5 Duplicated logic                | A-37 to A-72 | About 1500 lines, most of it a judgement       |

| 8 The smallest change             |              | Four commits that change no behaviour          |

## 2. Method, and how to read this

- **Mechanical checks.** Every `CONFIG_` symbol read against the Kconfig files and the other way
  round, every header against its includes, a clone search (runs of 8 or more identical lines after
  normalising: 25 runs outside the board directories), names in comments without a definition, and
  macros defined more than once.
- **Five reviewers** read the tree by area: the core with boot and command mode, the drivers, the
  ports with boards and arch, the host tools and the build, and the tests. They read only.
- **Re-checked.** The main claims were checked again at the site. An item marked † was not: it is a
  reviewer's reading.
- **Nothing was built or run.** "Byte-identical" below is a prediction and the check to make, not a
  result.
- **What the recommendations respect.** Code is not removed for having no user in the tree, but
  files nothing references and headers nothing includes may go (D-020). The wire and the image
  format are fixed (D-008). A board's storage layout is its own (D-026). The host tools mirror
  `wire.h` by hand (D-021). A unit test fakes its neighbours (D-007).
- **Ids.** A-nn names an item of this audit, so that a later change can say which one it does. None
  of the items was in `findings.md` or `findings-closed.md` on the day, except where an item names
  its finding.

## 4. Assumptions that no longer hold

### 4.1 In code

- **A-20. A key's status is read twice for every authentication.** `boot_image_auth_header()`
  (`src/boot/image_helpers.c`:87, :94) and the token check (`src/cm/cm_auth.c`:30, :35) call
  `rot_read_key_status()` and then `rot_get_dsa_key()`, which calls it itself (`src/rot.c`:146).
  That is two OCOTP reads on HAB and two SCU calls on the 8X, on the boot path (D-023), since
  `7431b64f` (2023). In `rot_get_dsa_key()` the checks at :143 and :153-154 can't fail after the
  status call succeeded. Change: drop the outer call at the two sites; the return codes stay, one
  log text changes ("Read key status failed" becomes "Get DSA key failed"). The fakes in
  `tests/unit/test_image_helpers.c`:85-99 and `tests/unit/test_cm.c`:563-576 model the two calls and
  need folding.
- **A-21. The watchdog's clock is ungated twice in a row.** `src/plat/imx6ul/plat.c`:402 and again
  at :417 under `CONFIG_ENABLE_WATCHDOG`; `src/plat/imx8m/plat.c`:366-367 and again at :377-378. The
  unconditional writes are from 2026-11-10 (`8ebbbc7e`, `38f1dd1f`), the conditional ones from 2023
  and 2024. The RT has the same structure without the repeat. Change: drop the conditional copies.
  The end state is the same; the register trace is one or two writes shorter, so the port tests'
  expectations may need the write removed.
- **A-22. `src/drivers/timer/imx_gpt.c`:66-68 waits for its software reset without a bound.**
  `drivers.md` 3 says every wait is bounded, `MMIO_POLL_HANDSHAKE` (`include/pb/mmio_poll.h`:26-28)
  is for a controller's own reset, and `imx_uart.c`:38 uses it so. F-462 lists the UART and PLL
  waits, not this one. Change: `mmio_poll_32(gpt_base + GPT_CR, GPT_CR_SWR, 0, MMIO_POLL_HANDSHAKE)`
  and return its error. Only the failure changes: an error where there was a hang. No unit test
  covers `imx_gpt.c` †.
- **A-23. `struct gpt_table_list.variant` is set by every board and read by nothing.**
  `include/drivers/partition/gpt.h`:28; the wire's variant is the array index (`gpt.c`:611-614). Do
  not remove it: the struct is the boards' (D-020). Either say in `gpt.h` that the index is the
  variant, or check `tables[i].variant == i` at the set up. Looking the layout up by the field would
  change what an existing host command installs.
- **A-24. e.MMC fields nobody fills or reads †.** `power_off_long_time_ms`
  (`src/drivers/mmc/mmc_core_private.h`:62) is only logged, while `mmc_power_off()`'s comment
  (`mmc_emmc.c`:1089) says it bounds the power off; the bound is the uSDHC's fixed 5 s.
  `struct mmc_device_info`'s `ocr_voltage` is written nowhere, and for an e.MMC `mode` and `width`
  stay at their invalid values. `max_chunk_bytes == 0` means "no limit" in `mmc_core.c`:190 and "a
  chunk of 0 bytes" at :239-243. Change: correct the comment and say in `mmc_core.h` what the struct
  holds; using the field as a bound would be new behaviour.
- **A-25. `default_boot_source` is always `BOOT_SOURCE_BIO` †.** `include/boot/boot.h`:51; set at
  `src/board.c`:82 and in all 11 initialisers of `tests/unit/test_boot.c`, read once at
  `src/boot/boot.c`:72. Boards no longer build this struct.
- **A-26. FlexSPI †.** `imx_flexspi_busy_wait(cfg, polling_time_us, timeout_ms)` gets a millisecond
  figure as its microsecond poll interval at `imx_flexspi.c`:403-404 and :561. :659-660 drops
  `bio_set_private()`'s result. `FLEXSPI_CONFIG` is handled (:308, :319) but no caller can pass it.
  Flag only: the poll interval changes how often the status command goes out, so measure before
  changing.
- **A-27. cdns3 endpoint set up †.** `cdns3_udc_core.c`:731 writes `CDNS_USB_EP_IEN` (not OR) inside
  the loop, so only the last endpoint's bits stay set, under a comment copied from :847; :726
  hard-codes the bulk type and :724 ignores `select_ep()`'s error. The driver polls and works on the
  MEK. Flag only: do not change the write without the bench.
- **A-28. A platform's mandatory drivers are prompts †.** `DRIVERS_IMX_GPT`, `DRIVERS_IMX_WDOG` and
  `DRIVERS_FUSE_IMX_OCOTP` are options a defconfig must turn on, though `plat.c` calls them
  unconditionally (with one off the link fails; from reading, not from a build). Other drivers are
  selected (`src/plat/Kconfig`:15-19, :53-55, :65) or added by the platform's makefile.
  `MAX_MMAP_REGIONS` and `MAX_XLAT_TABLES` get the same `default 32 if PLAT_...` in three Kconfig
  files. `platform.md` 6.1 asks for part of this, so it is a contract question first.

## 5. Duplicated logic

### 5.1 Core, boot and command mode

- **A-37. `board_setup()` writes "set up the boot driver, return the step's error" eight times.**
  `src/board.c`:123, :150, :165, :173, :184, :194, :209 and :219, each

- **A-38. `cm_cmd_auth()`: the token block and the password block.** `src/cm/cm_auth.c`:153-171 and

  called once per method. `tests/unit/test_cm.c`:1919-1944 runs a table of failures per method.
- **A-39. The position of a partition's bpak header is computed in three places.**
  `src/boot/boot.c`:277-284, `src/cm/cm_part.c`:85-96, and :288 with :311-314. The three answer a
  partition that is too small differently, and that must stay. Change: one helper that gives the LBA

- **A-40. `first_candidate()`'s A and B branches are mirror images.** `src/boot/ab_state.c`:334-363
  and :364-393, 30 lines each; the pairing is spelled out again at :442-450 and :528-535. Change: a

- **A-41. `boot.c`'s partition path and stream path are the same sequence †.** :289-309 and :328-364

  at four sites, and `boot_jump()` repeats its three-line exit three times. Change: one static
  function for both paths; the in-place path stays apart. Medium risk: it is the verification
  sequence.
- **A-42. The handovers repeat the same part lookups †.** "The entry's part exists and has at least
  n hashed bytes" five times (`image.c`:59-78, `atf.c`:152-171 and :188-212, `optee.c`:104-121,

  `boot.c`:622-636 and `optee.c`:139-150. About 60 lines. The log texts must stay with the callers:

- **A-43. The fail-closed presets of `plat_status` are written twice †.** `src/boot/boot.c`:410-414
  and `src/cm/cm_main.c`:554-559. Change: one core helper with all three presets.
- **A-44. `policy_fixed.c` is `policy_chain.c` with a list of one †.** About 60 of 96 lines. They

  on `size` at :173.
